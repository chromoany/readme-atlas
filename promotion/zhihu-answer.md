# 知乎回答版（约 700 字，短版）

> 用法：找相关问题（"怎么给开源项目写 README""AI 写的文档能信吗""README 应该包含哪些内容"），把这个回答贴过去，末尾自然带一次专栏链接。回答区的流量远大于专栏。

---

大部分人写 README 卡在第一步：不知道从哪句开始。让 AI 代写往往更糟——章节是全的，安装命令是编的。

我把这两件事拆开处理了。

先说结构。我读了 200 个开源项目的 README，全部要求 1,000 star 以上，每份固定到具体 commit。32 个写成详细案例，另外 168 个按 14 个领域分组，每组 12 个。结论是它们不能套同一个模板：Linux 的读者找的是开发入口，Godot 的用户只想下载编辑器，周刊的读者想先看最新一期。同样一份"简介—安装—使用—贡献"往下填，总有一处别扭。

再说事实。AI 写 README 最容易出的问题不是文笔，是凭空造细节。`pip install xxx` 这个包根本没发布，配置项代码里不读，路线图上的功能写成现在就能用。这些错误读者一复制就暴露，而且作者自己常常看不出来，因为写的时候就没查。

我做的 Skill（叫 README Atlas）强制两件事：写之前先从仓库里取出事实——清单文件、入口、示例、测试、CI 配置；写的时候只写取到的东西，取不到就把那句话删掉，不改成更模糊的说法。改写比删改更危险，一句假话经过两轮润色会变得更像真的。

实际用起来是这样：给出一份故意写错的草稿，里面自称"最快、生产就绪的日志平台"，还写了 pip 安装命令；但仓库里只有本地脚本，没有发布包也没有性能测试。改完之后的介绍是——这是个本地脚本，需要 Python 3.10+，不用装任何东西，命令怎么敲，跑完输出什么，最后补一句"日志级别必须在行首才会匹配"。

这个例子很小，但正好落在最常被卡住的地方。

安装是一行命令，装进 Claude Code、Codex、Cursor 这类 agent：

```bash
npx skills add chromoany/readme-atlas
```

它也管排版：徽章集中在顶部一块，正文左对齐，该有的截图放前面。这些细节在 13 个项目的视觉案例里拆开讲过。

局限也说清楚：200 个仓库研究的是结构，不是质量，它只能告诉你形状对不对，不能告诉你项目值不值得用。而且是 Markdown 指令，不是 linter，没有 CI 会在你写了无出处的命令时报错，还得靠 agent 真去看仓库，比直接生成慢。
